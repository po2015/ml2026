关于多语言项目，有一个不太舒服的事实：大多数 bug 不在翻译里。它们藏在你的代码和布局里——硬编码的英文字符串、装不下德语就截断的按钮、拒绝带重音符号姓名的表单、把阿拉伯语渲染成乱码的模板。等五种语言的翻译都付了钱才发现这些问题，意味着同样的问题要修五遍。

伪本地化的意义就是免费地把这些 bug 提前找出来。它是一种"假翻译"：把英文文本做机械变换，模拟真实翻译会带来的一切——拉长、加重音符号、套上括号——然后跑在你真实的界面上。现在会坏的东西，上线后一样会坏。

## 伪本地化到底做了什么

一次典型的伪本地化变换会把：

`Save changes` → `[Šàṽé çħàñğéš~~~ ąć]`

这一个字符串里发生了三件事：

1. **字符替换**：元音换成带重音的版本（à、ṽ、é）。编码问题会立刻暴露——如果你的技术栈没处理好 UTF-8，这些字符会渲染成 `Ã©` 或 `?`。
2. **膨胀**：字符串拉长 30–40%，模拟德语/俄语/西班牙语的文本长度。按钮、菜单、表格和对话框有没有空间，一目了然。
3. **边界标记**：括号（这里是 `[` 和 `ąć]`）包住每个字符串。被截断的文本会丢掉闭合标记，被裁剪的字符串一眼可见。拼接字符串——两个分别翻译的片段硬凑在一起——会在一个标签里出现两组标记，暴露出那些根本无法正确翻译的字符串。

有些方案还会加一个**镜像模式**，反转布局方向，在你还没有任何阿拉伯语文本之前，就能对阿拉伯语和希伯来语的从右到左（RTL）渲染做冒烟测试。

## 它能抓到什么（附真实案例）

- **硬编码字符串**：伪本地化运行后仍然是英文的任何文本，说明它从未被外置——译者永远看不到它，它会以英文原样出现在你的德语产品里。这是最常见的发现，没有之一。
- **文本被裁剪和重叠**：固定高度的列表项、固定宽度的导航、按英文表头定宽的表格。
- **字符串拼接**：`"Your order" + status + "was received"` 这种语序只在英文里成立；伪标记会把每一处都暴露出来。
- **编码故障**：带重音的字符在邮件、PDF、导出文件或数据库往返后变成乱码。
- **字体缺字**：缺失的字形显示为方框（tofu），远早于真实的中日韩或西里尔字符串出现在屏幕上。
- **无视区域设置的格式化**：日期、货币和数字被硬编码成单一格式。
- **字符串 ID 混乱**：重复或复用的字符串键——同一条英文源字符串服务两个语境，英文里没问题，但在需要两种不同译法的语言里就是错的。

## 怎么做

1. **生成伪语言环境。**大多数技术栈都有现成工具：i18n 库（i18next、FormatJS）的伪语言环境选项、Crowdin/Phrase/Lokalise 内置的伪本地化功能，或者给静态网站写个简单的变换脚本。对于 [Hugo 这类静态网站](/zh/news/website-localization-workflow/)，一个变换内容文件的脚本就够用了。
2. **把它当成一个真实语言环境加进去**（惯例的伪语言环境代码是 `en-XA`），这样整条语言管线——路由、回退、格式化——都会被真正跑到，而不只是字符串。
3. **走查真实用户路径。**注册、结账、表单、报错状态、邮件、PDF 导出、用伪文本做搜索输入。逐页截图胜过抽查。
4. **把每个缺陷记进两个桶**：代码问题（硬编码、拼接、编码）和布局问题（裁剪、溢出、方向）。修它们的是两拨人。
5. **修完重跑。**伪本地化便宜到可以放进 CI——有些团队直接用它卡住发布。

## 什么时候做

越早越好，但有三个时点最关键：

- **第一个翻译项目启动之前**：此时修复只是单语言的修复。翻译一旦开始，每处代码修改都可能让已翻译的字符串作废。
- **重大 UI 改动之后**：新页面和新组件会不断重新引入硬编码字符串。
- **新增一种文字系统或书写方向之前**：第一个中日韩语言、第一个 RTL 语言——永远先跑伪本地化。

跳过伪本地化的团队并没有跳过 bug；他们只是推迟到语言 QA 阶段才发现——那时修复要搭上翻译返工，或者推迟到生产环境——那时搭上的是客户。对一个典型的 B2B 网站做一遍伪本地化，一个工程师一两天就能完成，而且照例能翻出几十个问题——其中每一个，拖到以后都会更贵。
