一家制造商重做网站：选了 WordPress，理由是「大家都用」，再配一个流行的多语言插件。十八个月后，他们有了 5 种语言、每种语言 400 个页面，系统的吃力肉眼可见——插件的翻译编辑器丢字符串，每次更新都可能弄坏 hreflang 配对，从圣保罗访问要加载 6 秒，插件栈里还有两个插件只差一次漏掉的安全补丁就会让网站沦陷。没有人故意选错；他们只是用一个*通用*答案回答了一个*具体*问题。多语言 B2B 外贸网站的要求很不寻常——语言多、产品内容结构化、有翻译工作流、要全球都快、内部团队还小——CMS 决策应当从这些要求出发，而不是从市占率出发。下面是不加粉饰的市场全貌。

## 外贸网站到底需要 CMS 做什么

在比较名字之前，先把标准钉死——它们能快速淘汰大多数选项：

1. **分语言内容模型**：页面以 N 种语言存在，并有显式配对（供 hreflang 使用）、分语言 URL、元数据和媒体——而不是一个事后外挂的翻译层。
2. **翻译工作流**：内容能干净地导出给译者（XLIFF 或结构化文件）、无需复制粘贴就能回导，并且源文变更时能显示哪些译文已过时——[内容同步问题](/zh/news/multilingual-content-sync-maintenance/)是一个 CMS 功能，而不是靠自觉。
3. **全球性能**：在你的*目标*市场加载要快，而不是在你办公室快——这意味着静态输出或激进的 CDN 缓存，参见 [Core Web Vitals 及格线](/zh/news/core-web-vitals-b2b-exporters/)。
4. **结构化产品内容**：产品目录是数据（规格、型号、文档），不是自由排版的页面——CMS 应当用字段来建模它，既能支撑[买家期待的目录结构](/zh/news/product-catalog-website-inquiry-structure/)，也能输出机器可读的数据。
5. **小团队的总体拥有成本**：托管、更新、安全补丁、插件维护，以及出问题时需要的开发人力——按 3–5 年算，而不是按上线当天算。

## 四个现实的选项

| 选项 | 优势 | 对外贸网站的短板 |
|---|---|---|
| **WordPress＋多语言插件**（WPML/Polylang） | 生态庞大，到处都招得到人，起步便宜 | 翻译靠插件外挂；性能要靠缓存纪律维持；安全和更新是个停不下来的跑步机；多语言 SEO 上了规模就脆弱 |
| **传统企业级 CMS**（Drupal、TYPO3、Adobe AEM） | 真正的多语言架构、工作流、权限体系 | 对一个 5 语言的出口商网站来说，成本和复杂度荒谬；每改一点东西都要找专业代理 |
| **Headless CMS**（Contentful、Strapi、Sanity） | 干净的结构化内容、API 驱动、对翻译友好的内容建模 | 其他一切（前端、托管、表单、搜索）都要自己搭／组装；持续的 SaaS 费用；日常工作也依赖开发者 |
| **静态站点生成器**（Hugo、Astro、Next 静态导出） | 最快的输出、近乎零维护、便宜的全球托管、内容是文件，译者可以直接经手 | 非技术人员没有浏览器编辑器（除非搭配 git 系 CMS）；动态功能（搜索、表单）要靠外部服务 |

注意什么*不在*名单上：Wix／Squarespace／Shopify 式的建站器（做个宣传册可以，做 400 页 × 5 语言还带结构化规格就错了），以及自研 CMS（对一家主业是阀门而非软件的公司来说，永远不要）。

## 把选项和你的处境对上

**选 WordPress，当**你的团队本来就在用它、内容每周都在变、而且必须由市场人员（而非开发者）来发布。接受它要求的纪律：一个靠谱的多语言插件、一层缓存／CDN、由服务商搞定安全更新的托管，以及一条反对插件泛滥的铁律。管理良好的 WordPress 没问题；失败模式是*无人打理*的 WordPress。

**选静态生成器，当**内容变更是批量的（新品发布、季度更新）、网站以阅读为主（目录＋内容，无用户账户）、且速度和维护成本很重要——这几乎精确描述了大多数出口商网站。市场人员需要编辑就搭配一个 git 系 CMS 界面，[RFQ 询价](/zh/news/rfq-form-design-export-websites/)配一个表单服务。[托管决策](/zh/news/export-website-speed-cdn-performance/)变得微不足道（默认就是全球 CDN），[维护负担](/zh/news/website-maintenance-plan-exporters/)缩减为内容更新和依赖卫生。

**选 Headless，当**网站只是消费同一批内容的多个渠道之一（还有 App、门户、经销商外网），并且你有持续的开发能力。对单一的营销网站来说，它只是平白增加了活动部件。

**选企业级套件，当**你是一家有合规工作流、几十个市场、配着数字团队的大组织。读这篇文章的出口商几乎都不是。

## 决策清单

1. 谁发布内容、多久一次？（每周更新的市场人员 → WordPress 这一档；批量技术更新 → 静态。）
2. 三年内会有几种语言？（语言越多，结构化、文件化、对翻译友好的内容越值钱。）
3. 老实讲，五年维护预算是多少？（接近零 → 静态；「我们有代理年框」→ WordPress 可行。）
4. 目录数据今天以结构化形式存在吗？（有 PIM 或规格表 → 利于从数据渲染的静态／Headless；规格锁死在旧 PDF 里 → 不管选什么都得从[内容建模](/zh/news/product-catalog-website-inquiry-structure/)做起。）
5. 你的买家在哪里，网站在*那里*加载有多快？（从圣保罗、雅加达、利雅得测试候选方案，而不是从你的办公室——[速度架构](/zh/news/export-website-speed-cdn-performance/)问题往往直接终结 CMS 之争。）

正确的 CMS，是它的短板你能与之共处五年的那一个——而对大多数多语言外贸网站来说，这笔账越来越倒向简单、静态、结构化和快。我们的[网站建设团队](/zh/services/website-building/)正是在这样的技术栈上搭建出口商多语言网站——结构化内容、分语言 SEO、全球 CDN 速度、内置翻译工作流——而当 WordPress 对你的团队更合适时，我们同样实话实说。[描述一下你的情况](/zh/contact/)，如果我们自己的技术栈不合适，我们会劝你别用。
